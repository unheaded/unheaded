## 0. Honesty preamble — single-operator kingdom

**The kingdom is operated by Stevie Bellis solo.** This plan does not pretend a SOC team exists. It does not pretend a 24/7 on-call rotation exists. It does not pretend that the names "Sentinel," "BlackMage," and "MoatGhost" reference real people. These are **skill-personas** — procedural lenses Stevie adopts when wearing different hats. They are mode-switches, not headcount.

**What this means for response-time expectations:**

- **There is no 02:00 page.** No phone wakes up. No PagerDuty integration. No Slack-to-pager bridge. The detection sources (Sentinel daily loop, Mímir drift, Suricata IDS where deployed, security.yml CI, sbom-audit weekly, NVD/KEV feeds, manual operator observation, third-party report) feed dashboards and email — not pagers.
- **Median time-to-acknowledgement is operator-availability bound.** When Stevie sleeps, eats, drives, or is otherwise offline, alerts queue. The realistic acknowledgement window is **0-12 hours** during a normal day, **0-24 hours** on weekends or travel days, and **multi-day** during illness or vacation absent pre-arranged coverage.
- **There is no second pair of eyes by default.** Triage, containment, eradication, communications — every role in this plan is filled by the same person. This means **fatigue is a real failure mode** and the plan has to design around it. Long incidents must hand off to **third-party DFIR** or pause for sleep; they cannot run for 36 hours by one operator without quality collapse.
- **Forensic chain-of-custody is single-actor.** Stevie is the collector, the analyst, and the witness. For any incident with potential litigation or regulatory follow-up, this is **not adequate** — pre-engagement of a third-party DFIR firm is the only realistic mitigation.
- **The plan is testable, but the test is also single-actor.** Tabletop exercises (§9) are conducted alone. They are still useful — most of the value is procedural-recall — but they are weaker than multi-party tabletops.

**Sentinel SEN2 — accepted in full.** *"Today, no IR program exists. Detected incidents are surfaced in Sentinel summaries reviewed daily by Stevie when convenient. Median time-to-acknowledgement is unbounded. Mean time-to-resolution is undefined. Recovery from a real attack today is best-effort by a single operator."* This plan does not erase that condition — it converts it from "undefined and informal" to **"defined, time-bounded, and procedurally rehearsable."** That is the honest delta v1 buys.

**BlackMage BM4 — quantified in §10.** The 7-hour minimum dwell window between intrusion and morning coffee is an operating consequence of the alerts-only posture (ADR-043 hard condition #1) plus the no-paging condition. This plan does not eliminate that window in v1. It documents it, dollar-frames it, and sets the conditions under which v2 of the plan would close it (paging on P0, defined in §2).

## 1. Detection sources

The kingdom has eight production-or-near-production detection sources today. This plan codifies what each source produces, where the output goes, who sees it, and how fast.

| # | Source | Output | Destination | Cadence | Operator-review SLA |
|---|--------|--------|-------------|---------|---------------------|
| 1 | **Sentinel daily detection loop** | DGA / beaconing / exfil / lateral-movement candidates from Anamnesis Lite + Wotan logs | `~/sentinel-summary-YYYY-MM-DD.md` + email digest to stevie@bellis.tech | daily 07:00 CDT | next operator workday |
| 2 | **Mímir drift alerts** (heimdall-daemon, ADR-043) | byte-level drift events on UPC-managed config files | Wotan topic `drift.*` (unsigned per BM3 — known gap) + SSE on dashboard | continuous (1s scan tick) | next operator-attention window |
| 3 | **Suricata IDS** (where deployed) | rule-based network-IDS alerts (TTPs: T1071, T1041, T1110 candidate set) | `pkg/anamnesis/` ingestion → Wotan topic `suricata.alerts` | continuous | next operator-attention window |
| 4 | **security.yml CI workflow** | gosec / govulncheck / trivy / semgrep findings on every push | GHA run output + email-on-failure | every push + nightly cron | within 24 h on email |
| 5 | **sbom-audit weekly** | SPDX SBOM diff + license-policy violations | GHA artifact + email digest | weekly Sundays 04:00 UTC | within 7 days |
| 6 | **NVD / KEV feeds** (Sentinel via MCP) | CVE candidates against kingdom dependency graph | Sentinel summary (1) | daily | next operator workday |
| 7 | **Manual operator observation** | anomalies Stevie notices during normal work (slow service, weird log line, unfamiliar process) | tickets in Kanban / handoff-doc / direct ADR | continuous-while-awake | immediate when noticed |
| 8 | **Third-party report** | external researcher / adopter / drive-by report via SECURITY.md contact | stevie@bellis.tech | continuous | within 24 h on email |

**Single-operator-honest gaps:**

- **No paging.** Sources 1, 2, 3, 4, 6 all produce alerts; none page. They land in dashboards and email Stevie reads when next at a screen.
- **Source 2 (Mímir) is the highest-noise source by volume** and has the biggest "alerts → silence" risk per SEN2. Until a P0 page exists, Mímir is a forensic record, not a wake-up.
- **Source 3 (Suricata) deployment is unverified per SEN5.** If Suricata is not actually running on WEST + EAST, source 3 is documentation-only. Verifying and recording deployment status is open work tracked under F11.
- **Source 7 (operator observation) is the strongest source today.** This is uncomfortable but true — Stevie's pattern recognition on the kingdom's normal-state is the most reliable detection currently in production.

## 2. Triage criteria — severity, paging, and the percentage-based-consensus map

Per `docs/SERVICE_BREAKOUT_STRATEGY.md`, the kingdom uses a five-color percentage-based-consensus health scheme. Security events map onto the same colors so the dashboard never has two competing severity vocabularies.

### 2.1 Severity matrix

| Severity | Health-color | Hex | Trigger examples (security) | Operator action |
|----------|--------------|-----|-----------------------------|-----------------|
| **P3 (info)** | OK / Green | `#008000` | low-CVSS CVE in non-load-bearing dep; CI lint finding; sbom drift | logged; weekly review |
| **P2 (low)** | WARN / Yellow-Brown | `#fdda61` | medium-CVSS CVE; failed CI security check; benign-looking drift event | next operator workday review |
| **P1 (medium)** | ERROR / Bright Yellow | `#ffff00` | unexpected privileged process; multi-source drift event; new outbound connection to unknown IP; Suricata alert on known-bad TTP | morning-of review (≤ 24 h) |
| **P0 (high)** | CRITICAL / Neon Orange | `#ff5c00` | active intrusion suspected; key/credential compromise; signing key exposed; data exfil candidate observed; ransomware indicator | **immediate**, see §2.2 |
| **P0+ (panic)** | PANIC / Bright Red | `#ff0000` | confirmed compromise; persistence detected; auditable evidence of attacker hands-on-keyboard; regulatory-clock-starting event | **immediate** + external help engagement (§3) |

### 2.2 What gets paged immediately (P0/P0+)

**Realistic paging today:** none of the kingdom's existing channels are pagers. The current "page" mechanism is **Stevie noticing**. Until a v2 of this plan ships SMS/Pushover/PagerDuty integration, the procedural definition of P0 paging is:

1. **Email subject prefix `[KINGDOM-P0]`** to stevie@bellis.tech from Sentinel/Mímir/Suricata/manual-trigger.
2. **iOS/macOS Mail VIP rule** on stevie@bellis.tech — VIP-from `kingdom-alerts@*` plus subject-contains `[KINGDOM-P0]` → bypass Do Not Disturb (configured manually; not in the kingdom repo).
3. **Honest acceptance:** if Stevie's phone is on Do Not Disturb without VIP override, or off, or out of service, **paging fails silently.** This is the residual 7-hour dwell window from BM4. **It is not eliminated by v1.**

**v2 (out of scope for this document) will add:** Pushover or NTFY-style self-hosted push; SMS via Twilio or sip-trunk; explicit P0 escalation cron that retries every 15 min until acknowledged.

### 2.3 What waits for morning review (P1)

P1 events accumulate in the Sentinel daily summary email and on the dashboard. Operator reviews these once per workday during normal hours. No action outside business hours unless a P1 escalates to P0 via correlation (e.g., five P1s on the same host within an hour → automatic P0 promotion; this rule is **not yet implemented** — tracked as backlog item).

### 2.4 What waits for weekly review (P2/P3)

P2 + P3 events accumulate in the weekly sbom-audit + sentinel-weekly summary. Operator reviews these on a fixed weekday (Sunday morning, by current habit). They feed the security-debt backlog rather than triggering response procedures.

### 2.5 Severity-promotion rules (single-operator economy of attention)

- **Time-correlation:** ≥ 3 P2/P1 events within 60 min on the same host or same service → promote to P0. (Manual rule today; instrumentation backlog.)
- **Cross-source correlation:** any single host appearing in ≥ 2 detection-source feeds simultaneously (e.g., Mímir drift + Suricata alert) → promote one level.
- **Sensitivity context:** any event touching signing keys, Sealed Cask trust chain, Wotan ML-DSA-65 keys, GitHub deploy keys, or the macOS dev box → automatic P0 regardless of base severity.
- **Third-party-report:** any external report (source #8) is **never below P1**; an external researcher reaching out is itself a signal of severity by selection bias.

## 3. Escalation — the single operator's pre-established external bench

The honest single-operator IR concession is: **Stevie cannot run an extended IR alone.** Beyond ~8 hours of intensive response, fatigue degrades quality past the point where reactivity is net-negative. This plan therefore pre-establishes the external bench Stevie engages **before** that limit is hit, not after.

### 3.1 Pre-established escalation list (must be filled before this plan is operative)

| Role | Purpose | How engaged | When engaged | Status today |
|------|---------|-------------|--------------|--------------|
| **Privacy / breach-notification counsel (Barrister)** | regulatory-clock advice (GDPR 72h, HIPAA 60d-BA, state breach-notice laws), draft notification language, attorney-client privilege over IR work-product | retainer or pay-as-you-go relationship; phone + email | **within 1 h of P0+ confirmed compromise** suspecting personal data, regulated data, or contractual-notice triggers | **TBD — must be pre-engaged before this plan operates in earnest** |
| **Third-party DFIR firm** | forensic acquisition, malware analysis, attribution, expert testimony, second-pair-of-eyes on containment decisions | retainer or scoped engagement letter; on-call number | **within 2 h of P0+ confirmed compromise** with persistence or unknown TTP, OR when Stevie's continuous-response time exceeds 6 h | **TBD — must be pre-engaged** |
| **Breach-coach service** | 24/7 incident-coordination clearinghouse that warm-introduces Barrister + DFIR + PR + insurance carrier; bundles cyber-insurance benefit if applicable | hotline number on cyber-insurance card; or independent retainer | **within 1 h of P0+** as a single-call front-door instead of paging Barrister + DFIR separately | **TBD — depends on cyber-insurance status** |
| **Cyber-insurance carrier** | coverage confirmation; breach-coach activation; cost-recovery for forensics + notification | policy doc + claim hotline | **within 2 h of P0+ likely-claim event** | **TBD — kingdom does not currently hold a cyber policy; F12 backlog** |
| **GitHub Security (host platform)** | incident on the source-of-truth git remote: account compromise, deploy-key abuse, Actions runner abuse | https://github.com/contact/security + abuse-report flow | when intrusion vector implicates GitHub | always available (no pre-engagement needed) |
| **Cloud / hosting providers** (where applicable) | host-level forensics on managed infra; incident escalation on the platform | provider-specific abuse contact | per-provider | per-provider |
| **Law enforcement** (FBI IC3 / Secret Service for financial-instrument compromise) | criminal referral; not a response partner | https://www.ic3.gov/ | only after counsel advises | always available |
| **Adopter / community channels** | downstream notification when Sealed Cask / Wotan / kingdom artifacts are compromised in a way that affects adopters | SECURITY.md contact + GitHub Security Advisory | per §7 timeline | always available |

**Single-operator-honest concession:** **Today none of rows 1-4 are pre-engaged.** This plan operates in v1 *as if* they were, because pretending otherwise would mean writing a plan that can't be followed. Rows 1-4 are the **mandatory pre-condition** for this plan to be more than aspirational — pre-engaging them is the F12 / battle-plan follow-up tracked separately. Without rows 1-4, the kingdom's actual escalation today is: **Stevie alone, until exhausted, then degraded response or pause.** Document this explicitly in any post-mortem until rows 1-4 are filled.

### 3.2 Stevie's own escalation triggers

When Stevie should engage external help even if hesitant:

- **Personal data potentially involved.** GDPR / HIPAA / CCPA / state breach-notice clocks may be running. Counsel within 1 h.
- **Cryptographic root compromised.** Sealed Cask signing key, ML-DSA-65 topic keys, GitHub deploy key, SSH host keys → DFIR within 2 h to scope the blast radius before re-key.
- **Continuous active response > 6 h.** Hand off or pause; do not push to 12+ h alone.
- **Persistence beyond a single host.** Lateral movement across WEST ↔ EAST → DFIR within 4 h.
- **Adopter-facing artifact compromised.** Sealed Cask cassette, kingdom binary, public artifact → DFIR + counsel for downstream-notification language within 2 h.
- **Stevie is impaired** (illness, exhaustion, intoxication, emotional crisis) → DFIR or hand-off; **do not respond impaired.**

### 3.3 The "do not respond alone past midnight" rule

Operating discipline, codified: **for any P0+ event, if Stevie has been awake more than 16 hours, the next decision is "engage DFIR / pause for sleep" — not "push through."** Single-operator IR fatigue is the largest unforced-error generator in this plan's threat model.

## 4. Containment procedures (pointer-style — links to runbooks)

Containment is per-vector. This plan does not duplicate the technical details that belong in operational runbooks. Each row is a **pointer to the runbook** and a **single-operator caveat** about realistic execution time.

| Vector | Runbook | Quick-isolate command (pointer) | Realistic execution time (one operator) |
|--------|---------|--------------------------------|------------------------------------------|
| **Network — block remote IP** | `runbooks/security/firewall-audit.yaml` | `sudo iptables -I INPUT -s <BAD_IP> -j DROP` (per existing IR runbook step `block-suspicious-ip`) | 2-5 min once IP identified |
| **Network — isolate a service** | `runbooks/security/incident-response.yaml` (capture phase) + new runbook TBD | systemctl stop on host; or `kubectl scale --replicas=0` on K8s; or LXD-stop | 5-10 min |
| **Network — isolate a host (WEST or EAST)** | future `runbooks/security/host-isolate.yaml` (TBD — backlog) | iptables flush + SSH-only-from-VPN + suspend P2P link | 10-20 min |
| **Account — disable a user** | existing `disable-compromised-account` step in `incident-response.yaml` | `sudo usermod -L <user> && sudo passwd -l <user>` | 2 min per account |
| **Account — revoke API keys** | `runbooks/security/api-key-audit.yaml` + `secrets-rotation.yaml` | rotate keys via secrets manager; deploy + verify | 30-60 min depending on scope |
| **Account — revoke GitHub access** | manual: GitHub UI → Security → revoke sessions / deploy keys / OAuth grants | manual per-key action | 10-20 min |
| **Host — quarantine for forensics** | existing `incident-response.yaml` capture phase (DO NOT REBOOT until evidence captured) | `runbooks/security/incident-response.yaml` Phase 1 | 30-60 min for evidence-first quarantine |
| **Crypto — re-key signing roots** | future `runbooks/security/signing-key-rekey.yaml` (TBD — F2 backlog) | Sealed Cask key rotation + Wotan ML-DSA-65 rotation + GitHub deploy key replacement | 2-4 h end-to-end including re-issuance |
| **Crypto — rotate Wotan topic-signing keys** | future runbook (TBD); ADR-043 mentions "quarterly key rotation" | regenerate ML-DSA-65 keypair; redistribute via Gungnir | 30-60 min |
| **Application — kill a runaway service** | existing `runbooks/observe/service-health-sweep.yaml` | service health sweep + targeted stop | 5-15 min |
| **eBPF — detach kernel programs** | future `runbooks/security/ebpf-detach.yaml` (TBD) | `bpftool prog detach` per program | 5-10 min |

**Order of operations during containment** (single-operator economy of motion):

1. **Capture before isolating.** `runbooks/security/incident-response.yaml` Phase 1 commands run first — order-of-volatility rules apply.
2. **Network containment before account containment** (cuts off attacker faster than rotating credentials they may have already exfiltrated).
3. **Crypto re-key only after scope is bounded.** Re-keying before scope is known either misses contaminated keys or rotates clean keys uselessly.
4. **Document each containment action in `~/tmp/unheaded/docs/incidents/YYYY-MM-DD-<slug>.md` as it happens.** Memory degrades within hours; contemporaneous notes are evidence.

## 5. Eradication and recovery

Recovery in the kingdom takes one of three shapes depending on what was compromised. All three rely on the kingdom's existing trust-anchor: Sealed Cask (ADR-010) + the Git source-of-truth.

### 5.1 Service-level eradication

**Scope:** one or more application services (timeguru, captain, monad, sophia, etc.) running compromised code or compromised configuration.

**Path:**

1. Verify the kingdom's Git main is clean (no malicious commits since the last known-good tag).
2. Rebuild affected service binaries from clean Git via Sealed Cask (`scripts/build-sealed-cask.sh`).
3. Verify the resulting cask SHA-256 matches the manifest under the **rebuilt-from-clean** signing key (per §5.3 below if signing keys were also compromised).
4. Redeploy via the existing deploy runbook for the affected service.
5. Verify health via `runbooks/observe/service-health-sweep.yaml`.
6. Verify auth flows via `runbooks/security/api-key-audit.yaml`.

**Realistic time (one operator):** 30-90 min per service depending on Sealed Cask build duration on the build host.

### 5.2 Host-level eradication (rebuild WEST or EAST)

**Scope:** confirmed compromise of WEST or EAST bare-metal node.

**Path:**

1. Capture forensic image of the compromised host **before** any wipe (§6).
2. Quarantine the host on the network (full iptables shutdown + P2P link suspended).
3. Re-image from the kingdom's documented bring-up flow (per CLAUDE.md S-WEST bootstrap section + the equivalent for EAST).
4. Restore service state from clean Sealed Cask cassettes — **not** from any artifact pulled off the compromised host.
5. Re-establish P2P link via fresh WireGuard keys (the old WG keys are presumed compromised).
6. Verify cross-host BPF flow graph operational.
7. Verify all 10 services healthy via service-health-sweep.

**Realistic time (one operator):** 4-12 h per host depending on re-image automation + service redeploy + verification.

### 5.3 Cryptographic-root eradication (re-key signing roots)

**Scope:** any of: Sealed Cask signing key, Wotan ML-DSA-65 topic keys, SSH host keys, GitHub deploy keys, macOS-keychain-resident keys.

**Path:**

1. Generate fresh keys on a known-clean machine (the macOS dev box is **suspect by default in this scenario**; if compromise of the dev box is the working hypothesis, generate on a freshly-imaged machine instead).
2. Distribute fresh public keys via Gungnir / out-of-band channel.
3. Re-sign the current Sealed Cask cassettes under the fresh signing root.
4. Update `THIRD_PARTY.md` / SECURITY.md / wiki with the new public-key fingerprints.
5. Notify adopters via SECURITY.md channel + GitHub Security Advisory if downstream artifacts are affected (§7).
6. Revoke old keys: GitHub deploy-key revocation, Wotan topic-signing key revocation list, etc.

**Realistic time (one operator):** 2-6 h depending on number of roots affected.

### 5.4 Recovery-verification checklist (every recovery path closes with this)

- [ ] All services healthy (`runbooks/observe/service-health-sweep.yaml` returns green for all 10).
- [ ] Auth flows working (API key auth + JWT auth smoke per `runbooks/security/api-key-audit.yaml`).
- [ ] Sealed Cask SHA-256 chain verifies under the **post-incident** signing root (per `scripts/verify-binding-rune.sh`).
- [ ] Mímir reports zero drift on UPC-managed config files for 24 h post-recovery.
- [ ] Sentinel daily summary contains zero P0/P1 indicators for 72 h post-recovery.
- [ ] No unfamiliar processes / connections / cronjobs / systemd timers on rebuilt hosts (re-run `incident-response.yaml` investigation phase as a clean-state baseline).
- [ ] Post-mortem (§8) drafted within 7 days of recovery.

## 6. Forensics and evidence preservation

This section runs **before** §4 and §5. It is listed sixth here because the existing `runbooks/security/incident-response.yaml` already implements the procedural details and this plan should not duplicate them. **Order of volatility applies:** registers/cache → memory → network state → processes → disk. **Do not reboot until evidence is captured.**

### 6.1 Evidence sources

| Evidence | Source | Retention claim today | Retention reality (per SEN3) |
|----------|--------|------------------------|-------------------------------|
| Host process / network snapshot | `runbooks/security/incident-response.yaml` Phase 1 capture | written to `/tmp/ir-evidence-<ts>` on host | survives until `/tmp` tmpfs flush → must copy off-host immediately |
| Wotan log aggregation snapshot | `pkg/logagg/` ring buffer (10K entries) | "current" | **~10 seconds at moderate kingdom traffic** (SEN3) — must export ring-buffer to disk on incident-trigger |
| Anamnesis Lite eBPF event firehose | `pkg/anamnesis/` ring buffer | "current" | same 10-second wraparound risk |
| Suricata IDS alert log | `pkg/anamnesis/` ingestion + Suricata local logs | unverified per SEN5 | needs deployment-status confirmation before this row is real |
| Host disk image | manual `dd` or `dc3dd` to external media | n/a | requires pre-staged external storage; not currently provisioned |
| Memory image | manual LiME / AVML acquisition | n/a | requires kernel-module install; not currently provisioned |
| GitHub audit log (account-level) | github.com → Settings → Audit Log | 90 days for free tier; longer for Enterprise | depends on plan — verify and document |

### 6.2 Single-operator evidence-preservation procedure

1. **Trigger:** confirmed P0+ event.
2. **Step 1 — start a write-only IR log.** `~/ir-<ts>.md` open in a Markdown editor; every action and observation timestamped. This is the contemporaneous notebook; it is also the post-mortem source.
3. **Step 2 — run `runbooks/security/incident-response.yaml` Phase 1.** All capture commands.
4. **Step 3 — copy evidence off-host.** `scp /tmp/ir-evidence-<ts> govan@<other-host>:/var/forensics/<incident-id>/`. The "other host" is whichever of WEST/EAST is **not** suspected-compromised; if both are suspected, copy to the macOS dev box (and re-image the dev box later if warranted).
5. **Step 4 — export Wotan ring buffer.** `curl -sf http://wotan:18000/api/v1/logs/export?since=24h > /var/forensics/<incident-id>/wotan.jsonl` (endpoint exists per pkg/logagg dashboard contract; verify in v1 testing).
6. **Step 5 — export Anamnesis Lite eBPF event stream.** Equivalent dump endpoint or direct ring-buffer capture; document path during the first tabletop.
7. **Step 6 — disk imaging if warranted.** `dd if=/dev/<disk> of=/mnt/external/<incident-id>.img bs=4M status=progress conv=noerror,sync` — requires pre-staged external drive (open backlog item).
8. **Step 7 — GitHub audit-log export.** Manual download via UI or `gh api /orgs/<org>/audit-log` (if `gh` permission relaxed for IR; default kingdom posture is `git`-only per CLAUDE.md identity section).
9. **Step 8 — chain-of-custody note.** Append to IR log: who collected, when, where stored, hash of each artifact (`sha256sum /var/forensics/<incident-id>/*` → logged).

**Single-operator-honest caveat:** chain-of-custody with one collector who is also the analyst is **forensically weak** for litigation. If the incident may be litigated, **stop after Step 4 and engage DFIR** (§3) — let the forensic firm acquire under their own chain-of-custody procedures.

### 6.3 Retention floor (SEN3 acceptance)

Until pkg/logagg + Anamnesis Lite reach **90 days online retention** (industry floor, NIST AU-11), forensic windows are constrained to whatever export-on-trigger captures. This plan accepts that constraint and works with what exists. The retention floor is tracked under F7.

## 7. Notification timelines (regulatory + contractual)

**This is the section where wall-clock matters most.** Each clock starts on a different definition of "discovery." Counsel (§3.1 row 1) is the authoritative arbiter of when each clock starts in a real incident. The table below is the **operative checklist**, not legal advice.

| Framework | Trigger | Deadline | Recipient | Required content (high-level) | Realistic-today posture |
|-----------|---------|----------|-----------|-------------------------------|--------------------------|
| **GDPR Art. 33** | personal-data breach likely-to-result-in-risk to data subjects | **72 hours from awareness** | competent supervisory authority (DPA in member state of main establishment) | Art. 33(3) four mandatory fields: (a) nature of breach + categories + approx. record count; (b) DPO contact; (c) likely consequences; (d) measures taken / proposed | counsel-driven; kingdom is data processor in many adopter contexts → controller is the adopter, kingdom obligation is **prompt notice to controller** under Art. 33(2) |
| **GDPR Art. 34** | breach high-risk to individual rights | "without undue delay" after Art. 33 trigger | data subjects directly | clear & plain language description + DPO contact + likely consequences + measures | counsel-driven |
| **HIPAA Breach Notification Rule §164.404 (CE)** | breach of unsecured PHI by Covered Entity | **60 calendar days from discovery** | individual + HHS OCR + (if > 500) media | content per §164.404(c) | kingdom is **not a CE** by current architecture; this row applies only if the kingdom takes on a CE role (it should not) |
| **HIPAA §164.410 (BA)** | breach by Business Associate | **without unreasonable delay, no later than 60 calendar days** | the Covered Entity (the BA's customer) | nature + identifiers + dates + mitigation | applies if the kingdom is engaged as a BA — currently no BAA in force; tracked under HIPAA matrix headline gap |
| **PCI DSS 12.10.1** | suspected or confirmed cardholder-data compromise | "immediately" per the requirement; in practice "without unreasonable delay" | acquiring bank + card brands (Visa/MC/Amex/Discover) + PCI Forensic Investigator | per acquirer + brand notification matrices | kingdom should **never see CHD by architectural design** (PII-mode floor); this row activates only on architectural-floor breakdown |
| **SOC 2 CC7.3 / customer contractual notice** | "security incident" per MSA / DPA / SLA definition | per-contract; commonly 24-72 h | the customer / adopter | per-contract | adopter-MSAs not yet templated; SOC 2 Type 2 readiness backlog |
| **State breach-notice laws (US)** | varies by state; many have "personal information" + "unauthorized acquisition" + "risk of harm" | varies: 30 / 45 / 60 / 90 days; some "without unreasonable delay" | state AG and/or affected residents and/or credit bureaus | varies | counsel-driven; CCPA = California row below |
| **CCPA / CPRA** | breach of personal information of California consumers | "in the most expedient time possible and without unreasonable delay" | affected consumers + CA AG (if > 500 CA residents) | per CCPA §1798.82 | counsel-driven; kingdom is data processor / "service provider" role most often |
| **FTC Safeguards Rule (financial institutions)** | breach of customer information ≥ 500 individuals | **30 days from discovery** | FTC | per the Safeguards Rule | applies only if kingdom is a "financial institution" under GLBA — currently no |
| **NYDFS Part 500 §500.17(a)** | cybersecurity event likely-to-result-in material harm or required-notice-to-other-bodies | **72 hours from determination** | NY DFS Superintendent | per §500.17 | applies only if kingdom is a NYDFS-covered entity — currently no |

### 7.1 Single-operator notification realism

- **Counsel goes first.** Stevie does not draft notifications without §3.1 row 1 reviewing the draft. The single-operator-honest version of "we comply with GDPR Art. 33" is "**our counsel writes our Art. 33 notification, on our timeline; we provide them facts and act on their advice within the 72-hour window.**"
- **The 72-hour clock is wall-clock, not workday.** A Friday-evening discovery is a Monday-morning deadline. Pre-engaging counsel on a 24/7 retainer (or via a breach-coach service) is the only realistic mitigation.
- **Adopter-notification language is templated in advance.** A drafted "we have detected an incident affecting your data; here is what we know; here is what we are doing; here is how to reach us" boilerplate lives in `docs/legal/breach-notice-template.md` (TBD — backlog F7-adjacent). Drafting under time pressure during an active incident is how mistakes get made.

### 7.2 The internal-notification clocks

Independent of regulatory clocks, the plan defines internal milestones:

- **T+0:** detection / awareness.
- **T+15 min:** Stevie's IR log open; severity classified (§2).
- **T+1 h:** §3 external bench engagement decision made (engage or document why not).
- **T+4 h:** containment actions complete or in-progress with eradication path drafted.
- **T+24 h:** first written status update to any affected adopter (per contractual SLAs); first written internal status to docs/incidents/YYYY-MM-DD.md.
- **T+72 h:** GDPR-style notification deadline reached if applicable.
- **T+7 days:** post-mortem draft (§8).
- **T+30 days:** post-mortem published; action items tracked to closure.

## 8. Post-mortem template (blameless, ADR-style)

Every P1+ incident closes with a written post-mortem at `docs/incidents/YYYY-MM-DD-<slug>.md`. The template below is canonical; deviations require a sentence explaining why.

```markdown
# Incident YYYY-MM-DD: <one-line title>

## Status
<DRAFT | REVIEWED | CLOSED>

## Date(s)
- Detected: YYYY-MM-DD HH:MM <TZ>
- Contained: YYYY-MM-DD HH:MM <TZ>
- Resolved: YYYY-MM-DD HH:MM <TZ>
- Post-mortem published: YYYY-MM-DD

## Severity
<P0 | P0+ | P1 | P2 | P3>; final classification + any reclassification history.

## Summary
<≤ 5 sentences. What happened, when noticed, what was the impact, what was done.>

## Timeline
<UTC-stamped event log; entries copied from Stevie's contemporaneous IR log (~/ir-<ts>.md).>

## Root cause
<Five-whys or equivalent. Distinguish proximate cause (what triggered detection) from systemic cause (why the kingdom was vulnerable).>

## What went well
<Detection sources that fired correctly. Containment actions that worked. External-bench engagements that helped.>

## What did not go well
<Detection delays, containment fumbles, false starts, fatigue effects, communication gaps. Blameless: focus on systems, not the operator's failings.>

## Where we got lucky
<Distinguish "luck" from "skill". Honesty about what could have been worse.>

## Action items
<Numbered list. Each item has an owner (almost always Stevie), a target date, and a kingdom-tracker reference (battle-plan / Kanban / ADR / runbook backlog).>

## Notification record
<For each framework in §7 of IR plan: clock-start time, action taken, notification recipient + timestamp.>

## Evidence inventory
<Hash + location of every forensic artifact preserved. Chain-of-custody note.>

## Costs
<Operational hours by Stevie; external-bench billable hours; downtime cost; notification cost; insurance claim status. Map to §10 dollar-frame for retroactive calibration.>

## Doctrinal / architectural changes proposed
<New ADR drafts, runbook drafts, threat-model updates, control-matrix corrections, plan-version bumps to this IR plan.>

## References
<Links to: relevant ADRs; relevant runbooks; relevant threat models; battle plans; Kanban tickets opened.>
```

**Single-operator-honest discipline:** the post-mortem is **blameless** but it is **not blame-free of the system**. If the answer to "what did not go well" is "Stevie was tired," the systemic answer is "the plan should have engaged DFIR sooner" — that is a §3 / §3.3 corrective, not a personal failing.

## 9. Plan testing — tabletop exercises

A plan never tested is a plan that does not exist. The kingdom's tabletop cadence is sized for one operator.

### 9.1 Cadence

- **Quarterly:** one full-scope tabletop (4 h) covering one P0+ scenario from §9.2 selected by rotation.
- **Monthly:** one micro-drill (30-60 min) covering a single phase — detection, triage, containment, notification-draft, post-mortem-template — as a recall-only exercise.
- **Annual:** one **multi-party** tabletop with the §3.1 external bench (Barrister + DFIR at minimum). This is the **only** tabletop the plan considers fully valid; quarterly + monthly are recall-rehearsals, not validation.

### 9.2 Scenario library (start with these; add as the threat landscape changes)

1. **Sealed Cask signing key compromise.** Macbook stolen / phished / SSH-agent hijacked → attacker signs a malicious cassette → adopter notification plus full §5.3 re-key.
2. **WEST host compromise via known-CVE in unpatched dependency.** NVD/KEV feed flagged, patch SLA missed, attacker exploited → §5.2 host rebuild.
3. **Wotan topic injection on unsigned topic family** (per BM3 — `drift.*` / `audit.*` / `health.*`). Attacker forges audit events to mask intrusion → §5.1 service-level eradication + topic-signing scope expansion.
4. **Mímir alert flood-attack.** Attacker generates fake drift events to drown real signal → §2.5 promotion rules tested; backlog item to add Wotan-topic-signing on `drift.*` (per BM3) is exercised.
5. **GitHub deploy-key abuse.** Attacker uses a leaked deploy key to push a malicious commit to main → §5.3 + GitHub Security engagement.
6. **Zhen AI prompt-injection from poisoned vor sheet** (per BM6). Attacker plants a sheet whose retrieval causes Zhen to emit a Champion-bypassing tool call → §5.1 service-level + Champion-gate threat-model F1 follow-up.
7. **macOS dev box phish + SSH-agent hijack** (per BM5). Stevie clicks → attacker has live SSH access to WEST + EAST during the active session → §5.2 + §5.3 worst-case combined response.
8. **Third-party report on a vulnerability in a public kingdom artifact.** External researcher emails SECURITY.md → coordinated-disclosure timeline + GitHub Security Advisory + kingdom artifact patch.
9. **Adopter reports a downstream compromise** that traces back to a kingdom-published cassette → §7 adopter-notification + DFIR + counsel.
10. **Cyber-insurance-claim scenario.** Run the breach-coach call-tree once a year with the carrier (if a policy is in force) so the actual hotline is exercised.

### 9.3 Tabletop log

Each tabletop produces a short writeup at `docs/incidents/tabletop-YYYY-MM-DD-<slug>.md` mirroring §8's template (with "actual" rows marked simulated). Action items from tabletops feed the same backlog as real-incident action items.

Each bump is reflected in the plan filename (`ir-plan-vN-YYYY-MM-DD.md`); the prior version stays in the runbooks tree as a historical record. Tabletop and post-mortem templates copy the plan-version they were run under so artifact provenance is exact.

By inspection of §10.2, **pre-engaging the §3.1 external bench (counsel, DFIR, breach-coach, cyber-insurance) is the single highest-leverage item on the kingdom's security backlog.** It alone moves the plan from "aspirational v1" to "operative v1" and is responsible for ~50% of the modeled reduction. Estimated cost: **$5K-$25K/year retainer + $400-$700/h on activation**, which is **two-orders-of-magnitude below** the modeled annual-expected loss without it.

This is the BM10 dollar-frame restated: **the IR gap is not paperwork. It is the kingdom's single highest material cybersecurity exposure, costed.**
