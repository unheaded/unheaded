**Owner:** Stevie Bellis (sole operator; Principal IR Lead).
**Status:** draft until the signed `ir-plan-review` attestation (UH-IR-01) exists.
**Policy:** [information security policy](../../compliance/policies/information-security-policy.md) section 7. **Recovery:** [contingency plan](../../compliance/policies/contingency-plan.md). **Tested by:** [tabletop 2026-10-27](../../docs/incidents/tabletop-2026-10-27.md).
**Technical runbook:** `runbooks/security/incident-response.yaml` (evidence capture, investigation commands). This document decides; the YAML executes.

## 0. Ground rules

- One operator. No SOC, no rotation, no 24/7 coverage ([single-operator posture](../../compliance/policies/single-operator-posture.md)). The plan only promises what one person can do.
- Mail is the only pager. An incident that starts while the operator sleeps is found in the morning unless it is also loud enough to wake him.
- Capture before changing anything. Do not reboot a suspect host before section 6 step 2.
- Past 16 hours awake, the next decision is "pause" or "get help" (section 3), never "push through".

## 2. Severity and paging

Security severities use the ADR-029 consensus bands, so the dashboard has one vocabulary.

An availability incident with no sign of a security cause (a crash, an OOM, a full disk) follows ADR-100: its SLO alert, its runbook, and section 8 here. It uses this plan's sections 6 and 8, not the P-levels. The first sign of a security cause moves it here.

| Severity | Band | Examples | Response |
|---|---|---|---|
| P3 | OK (green) | low CVE in a non-load-bearing dependency; lint finding | weekly review |
| P2 | WARN | medium CVE; failed CI security gate; single benign drift event | next working session |
| P1 | ERROR | unexpected privileged process; drift on several files or both hosts; `AuthFailureBurst`; any third-party report | within 24 h |
| P0 | CRITICAL | suspected intrusion; credential or key exposure; exfiltration candidate; ransomware indicator | at once; section 3 decision within 1 h |
| P0+ | PANIC | confirmed compromise; persistence; attacker activity in progress | at once; capture, contain, get help |

**Promotion:** three P1/P2 events on one host or service within 60 minutes, or one host in two sources at once, goes up one level. Anything touching a signing key (commit GPG key, ML-DSA-65 evidence/drift keys, WireGuard keys, service token keys, GitHub deploy keys) is P0 regardless.

**Paging:** alert-mailer sends `page` urgency mail immediately (`observability/alerting/policy.yaml`, at most `max_per_day` mails). A P0 found by the operator or a third party is not paged by anything; the clock starts when it is read.

## 3. Contacts and help

| Who | For | Engaged |
|---|---|---|
| Stevie Bellis, stevie@bellis.tech | everything | always |
| GitHub Security | account, deploy key, Actions compromise | when the vector involves GitHub; no pre-arrangement needed |
| Anthropic support | Claude API key misuse or spend breach | `runbooks/security/claude-api-key-rotation-spend-breach.yaml` |
| Upstream maintainers | a vulnerability in a dependency | through their security policy |
| Privacy counsel, DFIR firm | notification advice, forensic acquisition | **none engaged.** Open decision with a default in [decisions for Stevie](../../docs/compliance/privacy/decisions-for-stevie.md) |
| Law enforcement (FBI IC3) | criminal referral | only after deciding to refer |

Get outside help when: personal data of someone other than the operator may be involved; a signing key is compromised; activity spans both hosts; response has run past 6 hours. With no bench engaged, "get help" today means: pause, contain hard (take the host off the network), and preserve evidence until help is found.

## 4. Containment

| Vector | Runbook | First action |
|---|---|---|
| Remote address | `runbooks/security/firewall-audit.yaml` | drop the source in nftables on the affected host |
| Suspect service | `runbooks/observe/service-health-sweep.yaml`, `runbooks/infra/systemd-service-debug.yaml` | stop the unit or container; do not delete it |
| Suspect host | `runbooks/security/incident-response.yaml` (capture first) | capture; then cut the LAN uplink, keep the P2P link only if the other host is clean |
| Account | `runbooks/infra/user-audit.yaml` | `usermod -L`; remove the authorized key |
| Service tokens and API keys | ADR-103; `runbooks/security/secrets-rotation.yaml` | `unheaded apikey revoke <prefix>`; remove the service's `.pub` from `trust.d` (revokes its tokens) and issue a new key pair |
| Leaked secret in git | `runbooks/security/git-history-secret-purge.yaml` | rotate first, purge second |
| TLS / CA keys | `runbooks/pki/ca-compromise-root-rotation.yaml`, `runbooks/security/tls-cert-rotation.yaml` | rotate after scope is known |
| Chaos run gone wrong | ADR-107 | `touch /run/unheaded/chaos/ABORT` (reverts within a second) |
| Wotan memory exhaustion | `runbooks/wotan/oom-state-recovery.yaml` | restart with the global budget; check rooms |

Order: capture, then network, then accounts, then keys (rotating keys before the scope is known misses some or wastes others). Record every action with its time in the incident file as it happens.

## 5. Eradication and recovery

Rebuild from git, never from the suspect host. Service, host and key recovery, recovery order and objectives are in the [contingency plan](../../compliance/policies/contingency-plan.md). Close every recovery with:

- every SLO in `observability/alerting/policy.yaml` green for 24 h;
- Heimdall reports no drift for 24 h;
- `go run ./cmd/compliance-evidence` shows no new FAIL against the pre-incident run;
- the restore drill passes if The Well was restored;
- a postmortem draft within 7 days (section 8).

## 6. Evidence handling

Evidence that already persists:

| Evidence | Where | Kept |
|---|---|---|
| Host and container logs | systemd journal on each host (bounded by `journald-caps`), shipped by Vector to ClickHouse `unheaded_logs.logs` | ClickHouse: 90 days, 455 days for rows labelled `audit` (`config/clickhouse/schema/001-logs.sql`) |
| Audit and health history | The Well `unheaded_ops`: `audit_events`, `service_health_transitions`, compliance journal and history tables; `llm_requests` | append-only (migrations 014-016); retention by partition, never row deletes |
| Drift events | Wotan `drift.*`, ML-DSA-65 sealed | as long as a subscriber stores them |
| Metrics | VictoriaMetrics / Prometheus | per the monitoring stack's retention |
| Code and config history | git, signed commits | permanent |

Procedure on P0:

1. Open `docs/incidents/YYYY-MM-DD-<slug>.md` from the [template](../../docs/incidents/TEMPLATE.md); log every action with UTC time.
2. Run `incident-response.yaml` capture steps on the suspect host. Copy the capture directory to the other host (or to removable media if both are suspect) and record `sha256sum` of each file in the incident file.
3. Export the relevant ClickHouse rows (by host, unit and time window) and the Well audit rows to the same place, with their hashes.
4. Only then contain (section 4).

One collector who is also the analyst is weak chain of custody. If the incident may end in court, stop after step 3 and get a DFIR firm.

Evidence collection reads metadata and logs of the platform itself; it does not read packet payloads or adopters' data.

## 7. Notification

The platform holds personal data of its operator only ([PII inventory](../../docs/compliance/privacy/pii-inventory-2026-10-27.md)); adopters run their own deployments. A breach of this deployment therefore usually triggers no regulatory clock. Where it might (an adopter's data reached through an artifact this project published, or third-party personal data in a report):

| Clock | Deadline | Applies when |
|---|---|---|
| GDPR Art. 33(2) (processor to controller) | without undue delay | this project processes an adopter's personal data (not the case today) |
| GDPR Art. 33 (controller to authority) | 72 h from awareness | personal data of others held here is breached |
| US state breach laws, CCPA | varies; most expedient time | as above, for residents of those states |
| Downstream adopters | as soon as scope is known | a published artifact (release, image, runbook) was tampered with: GitHub Security Advisory + `SECURITY.md` channel |

Counsel decides whether a clock started; none is engaged (section 3). Until one is, the operator writes facts only: what happened, what data, what was done, how to reach him.

## 8. Postmortems

Every incident meeting the ADR-100 threshold (an outage of Wotan, the dashboard, The Well or Zhen over 1 h; a silent failure over a day; a data-loss near miss; every P0/P0+) gets a blameless postmortem from `docs/incidents/TEMPLATE.md` within 7 days. Action items carry a register id, Kanban card or M-id.

## 9. Testing

- **Yearly:** one tabletop against a past incident or a scenario below, written up as `docs/incidents/tabletop-YYYY-MM-DD.md`; then re-attest `ir-plan-review`.
- **After each P0:** check this plan against what actually happened; bump the version if it was wrong.
- **Scenarios:** commit-signing key theft; host compromise through an unpatched KEV entry; forged Wotan events on an unsigned topic; leaked `uhk_` API key; Zhen prompt injection through a poisoned corpus sheet; tampered published artifact reported by an adopter; silent outage of the alert path (the 2026-10-27 tabletop).

## 10. What changed from v1

- Detection: Suricata removed; Heimdall, Vector, the rule files, Watchdog/heartbeat and the planned `detection.yml` named instead.
- Paging is real for `page` urgency (alert-mailer), no longer a mail-client VIP rule.
- The 90-day log retention floor v1 asked for exists for shipped journal lines (ClickHouse TTL); the Wotan and Anamnesis in-memory rings are no longer listed as evidence.
- Evidence handling points at append-only Well tables instead of `/tmp` captures alone.
- v1's per-intrusion dollar estimates are dropped: they were not derived from data about this project.
- The external bench (counsel, DFIR, breach coach, insurance) is still empty; v1 called it a precondition, v2 records it as an open decision with a default.
