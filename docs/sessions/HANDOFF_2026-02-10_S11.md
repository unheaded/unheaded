## What Was Done

### Kanban ↔ Timeguru Direct HTTP Polling

**Problem:** The kanban app had `Config.TimeGuruAddr` but never used it. The only timeline data path was Wotan gRPC subscription, which failed silently (wrong default port, protocol mismatch). Fallback was hardcoded stale tasks in `getInitialTasks()`.

**Solution:** Added direct Timeguru HTTP polling as a fallback alongside Wotan.

#### Data Flow (New)

```
Wotan path (preferred):  Timeguru → Wotan pub/sub → TaskManager → TimelineManager → Frontend
HTTP path (fallback):     Timeguru HTTP GET /timeline → Server.timelineManager → Frontend
```

Both paths feed the same `TimelineManager` (existing code, unchanged), which converts milestones/phases into kanban cards.

#### Changes to `cmd/kanban-app/main.go` (+143/-25 lines)

| Addition | Purpose |
|----------|---------|
| `Server.timelineManager` field | Standalone TimelineManager for HTTP polling mode |
| `getTimelineManager()` | Returns Wotan's TM when available, standalone TM otherwise |
| `fetchTimelineFromTimeguru()` | HTTP GET to `http://{TimeGuruAddr}/timeline`, parses `{"timeline":{...}}` |
| `pollTimeguru(ctx, interval)` | Initial fetch + 30s polling goroutine |
| Updated `handleGetTasks` | Falls back to timeline tasks from standalone TM |
| Updated `handleTimeline` | Uses `getTimelineManager()` instead of requiring taskManager |
| Updated `handleTimelineCards` | Three-tier: Wotan timeline → HTTP timeline → hardcoded fallback |
| Updated `handleSSE` | Sends initial timeline tasks from standalone TM |
| Updated `handleHealth` | Reports `timeline_http` and `timeguru_addr` |
| Fixed `TIMEGURU_ADDR` default | `localhost:8082` (was `localhost:9091` — wrong service) |
| Fixed `WOTAN_ADDR` default | `localhost:5555` (was `localhost:9090` — wrong Docker port) |

#### Changes to `cmd/kanban-app/wotan.go` (+1 line)

Added `"review": true` to `validateTask()` valid statuses. The frontend has a Review column but the validator only allowed `todo`, `in-progress`, `done`.
