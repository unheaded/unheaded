# ADR-096 — Dependency gate: trust only what costs an attacker something

**Status:** Proposed
**Date:** 2026-09-24
**Amends:** ADR-004 (its admission gate). ADR-004's aim, its exceptions
register and its replacement strategy stand.
**Related:** ADR-095 (the supply-chain track that will apply this gate one
dependency at a time), ADR-093 (a gate is not a gate until it has failed).

## Context

### What ADR-004's gate was for

ADR-004 admits a dependency only if it passes two checks: it comes from an
**established organisation**, and its **GitHub repository was created before
2019-07-01**. The ADR never wrote down the reason for the date. The reason,
from Stevie: keep out single-owner repositories generated by AI, which may
work on the surface but carry malware or run inefficiently. July 2019
predates AI coding assistants (Copilot's preview was mid-2021, ChatGPT late
2022), so the date stood in for "code written by people".

The aim is right. This ADR keeps it and replaces the evidence the gate
relies on.

### Why the two checks do not deliver it

Both checks read a property of the repository that an attacker controls, or
can buy.

- **Repository age is not code age.** A repository keeps its creation date
  when an old project is taken over, when a maintainer hands it on, or when
  new code is written into it, whether by a person or by an AI. event-stream
  (2018) and xz-utils (2024) were both old projects that changed hands. It
  also fails the other way: `protobuf-go`'s repository dates from 2019-03,
  but its code is a rewrite of a 2014 project.
- **"Organisation" is a free GitHub account type**, not a security team.
  `lib/pq` shows as an Organization and is run by volunteers.
- **Busy-looking activity is free to fake.** Contributors, stars, forks and
  one person's share of commits can all be manufactured with extra accounts.
  Git author names, emails and dates are fields the committer types in, so
  even a long history can be backdated. Splitting one person's commits
  across sock-puppet accounts makes a single-owner project look better
  distributed.
- **Approval happens once; risk keeps changing.** gRPC passed both checks,
  and by 2026-09-24 had two vulnerabilities govulncheck reports as reachable
  from Wotan, and nothing had re-checked it (ADR-004,
  "Register audit — 2026-09-24").
- **AI now suggests dependencies directly.** Assistants invent plausible
  package names that do not exist, and attackers register those names with
  working code ("slopsquatting"). That route does not go through a
  repository's age at all, and the assistants writing code in this
  repository are exposed to it.

### What the checks do and do not catch in this tree (measured 2026-09-24)

GitHub API, the 21 direct Go modules of the root module:

| module | repo created | owner type | top committer's share | ADR-004 verdict | what actually matters |
|---|---|---|---|---|---|
| `yuin/goldmark` | 2019-04-26 | User | 79% | fails the org check only | single-owner, and passes the age check |
| `sony/gobreaker` | 2015-05-29 | Organization | 77% | **passes both** | effectively one maintainer |
| `go-yaml/yaml` (`gopkg.in/yaml.v3`) | 2014-03-05 | Organization | 71% | **passes both** | **repository archived** (last push 2025-04-01); 22 production files import it |
| `cilium/ebpf` | 2019-09-05 | Organization | 48% | fails the age check | in use with no approval record |

The two checks passed an archived parser and a one-person library, and they
could not tell a volunteer group from a company. (The commit share is itself
a signal that can be faked; it is shown here only as a measurement, never as
a criterion.)

## Decision

### 1. Rank every signal by what it costs an attacker to fake

| class | signals | role in the gate |
|---|---|---|
| **Cheap** — an attacker can manufacture it | repo age, owner type, contributors, stars, forks, commit counts and shares, commit dates, README claims | **May reject. May never approve.** |
| **Anchored** — needs an identity or system the attacker does not control | established projects importing it (visible on deps.dev); independent distribution packaging (Debian, Fedora), whose maintainers are separate, vetted identities; vulnerabilities handled through a CVE Numbering Authority; independent audits; releases signed by an identity tied to a verified organisation domain (Sigstore/gitsign) | **Decides how much of it we must read.** |
| **Unfakeable** | our own reading of the code we build | **Decides admission.** |

Every reputation signal can be bought, borrowed or faked at some price, so
no signal approves a dependency on its own. Signals set how much review a
dependency needs; the review decides whether it gets in.

### 2. The gate, in order

1. **Minimise.** First ask whether the standard library or an existing
   `pkg/` package already does it. Every dependency not taken needs no
   trust. ADR-004's instinct stands.
2. **Human-named, and confirmed to exist.** A dependency enters only when a
   person names it and checks it on the registry: real release history, and
   the expected module path and owner. **No import goes in because an
   assistant suggested it**, and that includes the assistants working in
   this repository. This is the slopsquatting defence.
3. **Cheap signals screen out.** Reject if the repository is archived, has
   no release for a long time, is newer than the minimum age (§4), has
   changed owner or been renamed recently, or has open, unanswered security
   reports. None of these can approve.
4. **Anchored signals set review depth.**
   - *Several anchored signals* (for example, imported by major projects
     and packaged by a distribution): read the parts we call, and the
     parts that parse untrusted input.
   - *None*: the dependency must be **small enough to read in full, and we
     read it in full**. If it is too large to read, it does not get in; we
     write our own. This is where a single-owner, AI-generated project stops.
     Every cheap signal about it can be faked, and a full read cannot.
5. **Efficiency.** Benchmark it against the standard-library or in-house
   option on our real workload. ADR-004 already requires replacements to be
   "as fast or faster"; the same bar applies to admissions.
6. **Pin what was read.** A lockfile hash for Go and Rust, a hash-pinned
   `requirements` file for Python, a commit SHA for Actions, a digest for
   container images. The code reviewed is the code built. Any lockfile
   change that adds or bumps a module goes back through review.
7. **Record it.** One row in the exceptions register (ADR-004) and the
   ADR-095 supply-chain register, with every signal dated and cited, the
   review depth taken, the reviewer, and the owner's sign-off. A signal that
   was not checked is recorded as *not assessed*, never as a pass.

### 3. Re-check continuously, in a gate that is normally green

Approval is not permanent. On a schedule, and on every lockfile change:

- known vulnerabilities (govulncheck, `cargo audit`, OSV for Python);
- the repository archived, renamed or transferred;
- a new maintainer, or a first release by a new committer. A change of
  control **resets the review**; past reputation does not carry over;
- a new module in `go.sum` or `Cargo.lock` with no register row, which fails
  the build.

**This depends on CI being able to fail visibly.** Today `ci.yml` is
disabled and `Security Scan` has not passed in its last 100 runs (ADR-004
audit, finding 5). While that is true, none of this section exists. Getting
the security workflow green, so that red means something new, comes before
any new check is added to it. Each new check must be registered in
`scripts/check-gates-can-fail.sh` and watched failing (ADR-093 rule 1).

### 4. Replace the fixed date with a moving minimum

"Created before 2019-07-01" gets stricter every year and states no reason.
Replace it with **at least 3 years of release history** (proposed; see §6).
It stays a cheap signal: it can reject, never approve.

### 5. What this keeps from ADR-004

The aim, the exceptions register, the replacement strategy and its "as fast
or faster" bar all stand. The two original checks remain as screens; they
lose their power to approve.

### 6. Thresholds are set before measuring

These are proposals. Each is fixed in the register's header before the
first ADR-095 entry is reviewed, so no threshold is tuned to pass a
dependency someone already wants:

| threshold | proposed |
|---|---|
| minimum release history | 3 years |
| "no release for a long time" | 18 months, unless marked feature-complete with security reports still answered |
| "recently changed owner" | within 12 months |
| "small enough to read in full" | to be set per ecosystem once the first few entries have been reviewed |

## Consequences

**Good.** The gate measures what an attacker cannot buy. It stops the
single-owner, AI-generated project, because every cheap signal about it
can be faked, while a full read and anchored reputation cannot. It covers
the AI-suggestion route, which the old gate never saw. Admission stops being
a one-time event.

**Costs.** Reading dependencies is real work. The cost falls hardest on
small libraries with no anchored reputation, which is deliberate: that is
where the risk is.

**Honest limits.**
- Anchored signals lower the risk; they do not remove it. xz-utils was
  packaged by every major distribution. Section 3's reset on a change of
  control is the defence against that pattern, not reputation.
- A full read catches what a careful reader can see. It does not prove the
  absence of a subtle backdoor. The residual defence is the minimisation
  in step 1.
- AI-written code cannot be reliably detected from outside, and this gate
  does not claim to detect it. It asks instead for evidence a person
  reviewed the code, and it reviews the code itself.

   import it. Candidates: a maintained successor (verify its provenance

   use.

   with no approval record. Small enough to be candidates for a full read,
   or for replacement.
