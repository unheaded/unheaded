# NIST SP 800-207 Zero Trust Architecture Coverage Matrix

**Date:** 2026-05-06
**Author:** Marshal post-shift extension (NORTH-STAR Appendix A Phase E8)
**Reference:** NIST SP 800-207 (August 2020) — Zero Trust Architecture
**Approach:** ZTA is an *architectural framework*, not a control catalog. The matrix below maps the kingdom against (a) the 7 ZTA tenets, (b) the logical architecture components (PE / PA / PEP + data sources), (c) the deployment-variation patterns, (d) the trust algorithm requirements, and (e) the threats specific to ZTA itself.
**Status legend:** **MAPPED** = full coverage with evidence | **PARTIAL** = some coverage, gap noted | **GAP** = no kingdom work yet | **DEFERRED** = planned, not shipped | **UNVERIFIED** = MoatGhost confirm

**Kingdom posture (TL;DR):** The kingdom is **partially zero-trust by design** — Champion gate's per-action authorization, ML-DSA-65 topic signing on `config.*`, NetworkPolicy default-deny, and pkg/auth's per-request validation are all ZTA-aligned. **The kingdom is NOT yet a fully-realized ZTA** — the Policy Decision Point (PA) is implicit in code rather than externalized as a Policy Engine; trust algorithm inputs are scattered across components rather than fed into a unified policy engine; identity-based access still mixes with network-based access in places.

This is **PARTIAL ZT**, not full ZT. The maturity gap is documented explicitly.

## 7 ZTA Tenets (NIST SP 800-207 §2.1)

| # | Tenet | Status | Evidence / Gap |
|---|-------|--------|----------------|
| 1 | All data sources and computing services are considered resources | MAPPED | Wotan-as-message-bus pattern + The Well 3-database trust separation + per-service authentication. Every Unheaded service treats every other service as a resource requiring authentication. |
| 2 | All communication is secured regardless of network location | PARTIAL | TLS 1.3 mandatory regardless of internal/external; ML-DSA-65 PQC signing on `config.*` topics; QUIC/HTTP3 edge transport; NetworkPolicy default-deny within the namespace too. **No "internal network = trusted" assumption.** **SEN8 caveat:** NetworkPolicy enforcement on default kindnet CNI is unproven (per K8s threat model §3.3); requires Calico/Cilium switch OR live smoke test before promoting to MAPPED. **BM3 scope qualifier:** ML-DSA-65 signing scope is `config.*` topics ONLY; drift.*, audit.*, telemetry.*, health.* topic families are unsigned and forgeable. |
| 3 | Access to individual enterprise resources is granted on a per-session basis | PARTIAL | JWT TTL forces re-validation; pkg/champion 3-rule gate is per-call. **Gap:** no formal "session" object — JWT is the session proxy. Tightening per ADR-059 / CLI session work in Phase B tonight. |
| 4 | Access to resources is determined by dynamic policy — including the observable state of client identity, application/service, and the requesting asset | PARTIAL | pkg/champion checks: (1) the requested action against tool catalog, (2) the justification chain (retrieval-derived or direct-user), (3) the identity context. **Gap:** no asset-state input (device posture, geolocation, time-of-day) — the kingdom's trust algorithm is identity + justification, not the full ZTA TA. |
| 5 | The enterprise monitors and measures the integrity and security posture of all owned and associated assets | PARTIAL | Mímir / heimdall-daemon drift detection (REAL-METAL validated 2026-04-08); Anamnesis Lite eBPF traceability; Suricata IDS + Sentinel detection; cross-service health-monitoring percentage-based consensus. **Gap:** no formal "asset health score" feeding policy decisions — Mímir alerts but does not gate. |
| 6 | All resource authentication and authorization are dynamic and strictly enforced before access is allowed | MAPPED | pkg/auth.Middleware on every service; pkg/champion gate before every mutation; ML-DSA-65 verification before topic processing on `config.*`. Authentication is per-request, not per-session-only. **BM3 scope qualifier:** ML-DSA-65 signing scope is `config.*` topics ONLY; drift.*, audit.*, telemetry.*, health.* topic families are unsigned and forgeable. |
| 7 | The enterprise collects as much information as possible about the current state of assets, network infrastructure, and communications, and uses it to improve its security posture | PARTIAL | eBPF traces every packet from XDP; Wotan ring buffer; Anamnesis Lite event firehose; Sentinel daily detection loop with NVD/KEV feeds; trace_id propagation. **Gap:** the collected information is observed and alert-on, not yet looped back into policy decisions automatically. The "improve security posture" feedback loop is daily-batch (Sentinel) not per-request. |

**Tenet maturity summary:** 3 of 7 MAPPED, 4 of 7 PARTIAL. Two largest gaps: Tenet 4 (asset state in policy) and Tenet 7 (closed-loop posture feedback).

## ZTA Logical Architecture Components (NIST SP 800-207 §3)

The ZTA reference architecture has three core components plus data sources:

### Policy Decision Point (PDP) = Policy Engine (PE) + Policy Administrator (PA)

| Component | Status | Kingdom Equivalent / Gap |
|-----------|--------|--------------------------|
| **Policy Engine (PE)** — decides whether to grant access | PARTIAL | pkg/champion is the de-facto PE for mutations (3-rule gate). pkg/auth.RBACAuthorizer is the de-facto PE for reads. **Gap:** these are two separate PEs; not unified. Tonight's K8s RBAC review F1 shows the RBAC PE has a least-privilege failure. |
| **Policy Administrator (PA)** — generates session-specific authentication tokens, instructs PEP to allow/deny | PARTIAL | pkg/auth issues JWTs (the auth tokens); pkg/champion issues pending-confirmation tokens. **Gap:** these aren't a single coherent PA — token issuance is decentralized per service. |
| **Trust Algorithm (TA)** | PARTIAL | Champion's 3 rules (action allowlist, justification chain, identity trust label) are a TA. **Gap:** not formally documented as a TA; not parameterized; no continuous-evaluation logic. |

### Policy Enforcement Point (PEP)

| Component | Status | Kingdom Equivalent |
|-----------|--------|--------------------|
| **PEP** — enforces PE decisions; sits between resource and requester | PARTIAL | pkg/auth.Middleware on every service is the PEP for service ingress; pkg/champion is the PEP for mutating tool calls; HAProxy edge is the PEP for external traffic; NetworkPolicy is the PEP for pod-to-pod traffic. **SEN8 caveat:** NetworkPolicy enforcement on default kindnet CNI is unproven (per K8s threat model §3.3); requires Calico/Cilium switch OR live smoke test before promoting to MAPPED. |
| Multiple PEPs (mesh-style) | MAPPED | All of the above coexist — defense-in-depth pattern. |

### Data Sources feeding the Trust Algorithm (NIST §3.3)

| Source | Status | Kingdom Equivalent / Gap |
|--------|--------|--------------------------|
| **CDM system** — Continuous Diagnostics & Mitigation | PARTIAL | Mímir + heimdall-daemon (asset-state for hosts); Sentinel detection loop. Gap: asset-state is reported, not consumed by PE. |
| **Industry compliance system** | PARTIAL | sbom-audit.yml, security.yml, gpl-boundary.yml. Gap: results not fed to PE. |
| **Threat intelligence feed(s)** | MAPPED | NIST NVD + CISA KEV via MCP (Sentinel). |
| **Network and system activity logs** | PARTIAL | Anamnesis Lite eBPF; Wotan log aggregation; pkg/auth.AuditLogger. **SEN3 caveat:** Effective retention ~10 seconds at moderate traffic rate (10K-entry default); below FedRAMP / CIS 8.10 floor of 90 days online. Detection without retention is not coverage. |
| **Data access policies** | PARTIAL | The Well per-service users + RBAC. Gap: not centrally declared. |
| **Enterprise public key infrastructure (PKI)** | PARTIAL | TLS 1.3 cert chain; ML-DSA-65 PQC keys via cloudflare/circl. **Gap:** no central PKI for kingdom-wide signing identity (each service has its own key material). |
| **ID management system** | PARTIAL | pkg/auth (NoopAuthenticator dev / APIKey staging / JWT prod with OAuth 2.0 federation). Gap: no single ID-management service; federation is in JWTs only. |
| **SIEM** | GAP | No SIEM. Wotan log aggregation is closer but not SIEM-grade. |

## ZTA Migration Maturity (NIST SP 800-207 §7)

NIST identifies a maturity progression: **Traditional → Initial → Advanced → Optimal**.

| Pillar | Kingdom Maturity Today | Path to Next |
|--------|------------------------|---------------|
| Identity | **Initial → Advanced** (federated JWT path; per-service users; need MFA enforcement) | MFA enforcement + central ID service |
| Devices | **Initial** (eBPF observes; not feeding policy) | Asset-state input to PE |
| Networks | **Advanced** (default-deny + ML-DSA-65 + eBPF) | Calico/Cilium for kindnet enforcement; WireGuard overlay |
| Apps & Workloads | **Advanced** (Champion gate + Sealed Cask) | Unified PE |
| Data | **Initial** (per-service users; no data-classification labels feeding policy) | Data classification + label-based access |
| Visibility & Analytics | **Advanced** (eBPF + Wotan + Sentinel) | SIEM correlation |
| Automation & Orchestration | **Initial** (CI/CD + Marshal enforcement; not policy-driven response) | Closed-loop response |

**Aggregate maturity:** the kingdom is in **Advanced** for Networks, Apps, Visibility; **Initial** for Devices, Data, Automation; **Initial-bridging-Advanced** for Identity. **Optimal** is the long-horizon target.

## Headline gaps (priority for ZTA maturation)

1. **Unify the Policy Engine.** pkg/champion + pkg/auth.RBACAuthorizer + NetworkPolicy together act as a federated PE; consider a single PolicyDecisionService that all three consult (or that they all delegate to). High-leverage refactor.
2. **Asset state in the Trust Algorithm.** Mímir + Sentinel produce asset-state and threat-state but don't feed it into Champion. Closing this is the single highest jump in ZTA maturity.
3. **Central PKI for kingdom signing identity.** Today each service has its own key material; ZTA Optimal expects an enterprise PKI. cloudflare/circl + ML-DSA-65 are the substrate; needs the management plane.
4. **MFA enforcement on privileged actions.** Currently UNVERIFIED in pkg/auth — declare the enforcement explicitly or document the gap.
5. **Closed-loop response from Sentinel detection back to PE.** Today Sentinel detects and alerts; ZTA Optimal would have detection trigger automatic policy adjustment (e.g., suspend-suspicious-token).

## Where the kingdom is already strong

The **eBPF-everywhere** posture (Anamnesis Lite, Mímir, flow-tracker) gives the kingdom data-source coverage that most ZTA implementations struggle to achieve. The **Champion gate** is a textbook PEP for mutations. **TLS 1.3 + ML-DSA-65 + NetworkPolicy** triple-defense maps directly to ZTA Tenet 2. Document these as the kingdom's ZTA story.
