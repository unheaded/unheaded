## Is There a Fee?

**No.** Submitting Internet-Drafts to the IETF is completely free. There are no fees at any stage:
- No submission fee
- No review fee
- No publication fee
- No IANA registry fee

The IETF is an open standards organization. Anyone can submit an Internet-Draft. The only cost is your time writing and formatting the document.

## The Path: Internet-Draft → RFC

```
1. Write I-D (Internet-Draft)
   ↓
2. Submit via IETF Datatracker
   ↓
3. I-D published in IETF repository (public, no formal status)
   ↓
4. Present at IETF meeting / mailing list discussion (optional but recommended)
   ↓
5. Working Group adoption (WG chairs decide to take it on)
   ↓
6. WG review + revision cycles
   ↓
7. IETF Last Call (community-wide review)
   ↓
8. IESG review + approval
   ↓
9. RFC Editor processing
   ↓
10. Published as RFC (permanent, immutable)
```

**Timeline**: 1-5 years from first I-D to RFC. Some go faster (6 months with WG support), some never make it.

**Individual submissions** (no WG): Can go directly from I-D → IESG review → RFC, but this path is harder and less common.

## Step-by-Step Submission Process

### Step 1: Write the Draft

**Naming convention**: `draft-{lastname}-{topic}-{version}.{ext}`
- Our format: `draft-bellis-unheaded-protocol-foundation-06.xml`
- Version starts at `00`, increments with each revision
- Name MUST start with `draft-`

**Format**: The IETF accepts two source formats:
1. **XML (RFCXML)** — preferred, machine-readable (`xml2rfc` format)
2. **Plain text** — legacy, being phased out

**Output**: Both produce formatted plain text and HTML versions.

### Step 2: Format with Tools

**Required tools** (all free, open source):

| Tool | Purpose | Install |
|------|---------|---------|
| `xml2rfc` | Convert RFCXML to text/HTML | `pip install xml2rfc` |
| `kramdown-rfc` | Write in Markdown, convert to RFCXML | `gem install kramdown-rfc` |
| `mmark` | Alternative Markdown → RFCXML | `go install github.com/mmarkdown/mmark/v2@latest` |
| `id-nits` | Validate I-D formatting | `pip install id-nits` or online at https://author-tools.ietf.org/ |

**Recommended workflow for us**: Write in Markdown → `kramdown-rfc` → RFCXML → `xml2rfc` → formatted output.

### Step 3: Validate

Before submitting, validate your draft:
```bash
# Check formatting
xml2rfc --check draft-bellis-unheaded-protocol-foundation-06.xml

# Run idnits (checks IETF compliance)
idnits draft-bellis-unheaded-protocol-foundation-06.txt

# Or use the online tool:
# https://author-tools.ietf.org/
```

Common validation issues:
- Lines > 72 characters
- Missing boilerplate text (copyright, IETF trust)
- Missing IANA Considerations section
- Missing Security Considerations section
- Incorrect date format

### Step 4: Submit

**Submission URL**: https://datatracker.ietf.org/submit/

1. Go to the IETF Datatracker
2. Log in (create a free account if needed at https://datatracker.ietf.org/accounts/create/)
3. Click "Submit a new Internet-Draft"
4. Upload your XML source file
5. The system generates text and HTML versions automatically
6. Confirm and submit

**What happens next**:
- The I-D appears in the IETF I-D repository within minutes
- It gets a permanent URL: `https://datatracker.ietf.org/doc/draft-bellis-unheaded-protocol-foundation/`
- An announcement is sent to the `new-ids` mailing list
- The draft expires after 185 days if not updated

### Step 5: Engage the Community

After submission:
- **Mailing lists**: Find relevant IETF working groups
  - `6man` (IPv6 Maintenance) — for Hop-by-Hop extension header usage
  - `intarea` (Internet Area) — for protocol architecture
  - `bpf` — if there's a BPF-related WG
- **IETF meetings**: Present at the next IETF meeting (3 per year, registration ~$800 for in-person, free for remote)
- **Hallway conversations**: Network with area directors

### Step 6: Working Group Adoption

To get adopted by a WG:
1. Present the draft at a WG meeting
2. WG chairs call for adoption (mailing list consensus)
3. If adopted: `draft-bellis-unheaded-*` → `draft-ietf-{wgname}-unheaded-*`
4. WG drives further review and revision

## Required Sections in Every I-D

Every Internet-Draft MUST contain:

1. **Abstract** — Brief summary (1 paragraph)
2. **Status of This Memo** — Boilerplate (auto-generated by xml2rfc)
3. **Copyright Notice** — IETF Trust boilerplate (auto-generated)
4. **Introduction** — Problem statement and motivation
5. **Terminology** — RFC 2119 keywords (MUST, SHOULD, MAY, etc.)
6. **Body** — The specification
7. **Security Considerations** — REQUIRED, even if "no security impact"
8. **IANA Considerations** — Registry requests, or "This document has no IANA actions"
9. **References** — Normative (MUST cite) and Informative (helpful context)
10. **Author's Address** — Name, organization, email

---

## IANA Registry Requests

Our drafts request 12+ IANA registries. The IANA Considerations section must specify for each:

```
Registry Name: Monad Protocol Version Numbers
Registration Procedure: Standards Action
Reference: [this document]
Initial Values:
  Value  | Description           | Reference
  0x01   | Foundation v1 (frozen)| [this document]
```

**IANA review happens during RFC publication** — not at I-D submission. But defining registries early shows maturity.

## Unheaded-Specific Submission Strategy

### Phase 1: Submit Foundation draft-06 as Individual I-D
- No WG needed initially
- Establishes the wire format in the IETF record
- Gets community feedback on HbH option usage

### Phase 2: Engage 6man WG
- The IPv6 HbH extension header usage should be reviewed by 6man
- They may have concerns about HbH option proliferation
- Address RFC 8200 §4 compliance

### Phase 3: Submit Sophia + Wotan as companion I-Ds
- Reference the Foundation I-D
- Show the complete protocol suite

### Phase 4: IANA Registration
- Once any draft progresses toward RFC, IANA allocates the registries
- Our HbH option type (0x3E) would get an official assignment
